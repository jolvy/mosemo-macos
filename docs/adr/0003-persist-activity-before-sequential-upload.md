# 활동 레코드를 먼저 영속 저장하고 기존 API로 순차 전송한다

## 배경

네트워크 오류와 서버 응답 유실은 온라인에서도 발생한다. 연결 상태에 따라 저장
경로를 나누면 순서와 재시작 복구를 함께 보장하기 어렵다. 목표는 저장된 대기
레코드를 보존하고 순차 전송하여 최종 관찰 타임라인이 수락된 원본에 수렴하는
것이며, 보관 기간 대신 저장 용량으로 한계를 정한다.

## 결정

- 개인정보 필터를 적용한 모든 활동 관찰·수집 상태 변경은 온라인에서도 암호화된
  영속 대기열에 먼저 저장한다. 식별자·Device 순번·본문과 다음 순번은 원자적으로
  보존하며 계정·Device별로 분리한다.
- 앱 내부 비동기 전송기가 같은 Device의 가장 오래된 레코드부터 기존 단건
  활동 등록 API를 사용한다. 한 번에 한 요청만 진행하며 일치하는 수락 응답을
  확인해야 제거하고 다음 레코드를 보낸다. 별도 OS 프로세스와 배치 API는 두지 않는다.
- 응답 유실은 저장된 동일 식별자·순번·관찰 시각·본문 재전송으로 복구한다.
  서버의 기존 멱등 수락 계약을 사용하며 연속 순번 ACK는 요구하지 않는다.
- 용량 한도에서 대기 기록을 버리지 않고 수집만 중단한다. 전송 가능한 기존
  기록은 처리하고 충분한 공간과 사용자 설정·권한·계정 조건이 회복되면 자동
  재개한다. 충돌은 전송을, 저장소 손상은 수집과 전송을 중단하며 기록을 보존한다.
- 일반 로그아웃·토큰 만료·Device 거절은 폐기 근거가 아니다. 기기 전환의 유실
  예외는 별도 서버 ADR-0006과 후속 인증 계약이 소유한다.

저장 엔진의 제품 선택은 이 결정으로 고정하지 않는다. 기존 SQLite 암호화
대기열은 구현 후보이며, 핵심 계약은 영속성·원자성·암호화·복구와 계정 격리다.

## 고려한 대안

- **온라인 직접 전송, 오프라인에서만 저장**: 요청 중 장애와 연결 상태 경합마다
  다른 복구 경로가 필요하다. 일관된 보존·순서 계약을 위해 채택하지 않았다.
- **영속 대기열과 배치 API**: 처리량 개선 여지는 있으나 부분 수락과 재시도
  계약이 추가된다. 현재 요구는 기존 단건 API로 충족 가능하므로 보류한다.
- **별도 프로세스 전송기**: 앱 종료 중 처리에는 유용하지만 프로세스 간 저장·키·
  인증과 배포 책임이 늘어난다. 다음 앱 실행에서 이어 보내는 요구에 맞춰 보류한다.

## 결과

- 로컬 저장 비용을 온라인에서도 부담하고 단건 ACK 지연이 밀린 기록의 처리량을
  제한한다. 측정으로 병목이 확인되면 배치 전송을 후속 검토한다.
- 선두 레코드의 영구 오류는 후속 전송을 막는다. 오류를 숨기기 위해 건너뛰거나
  자동 삭제하지 않으며 새 관찰은 가능한 용량까지 보관한다.
- 앱 종료 시 서버 전송 완료를 기다리지 않는다. 이미 영속 저장된 기록은 다음
  실행에서 복구하고 정상 종료는 진행 중인 로컬 저장을 안전하게 마친다.
- 대기열 변환과 암호화 키 복구는 보존 계약의 일부다. 실패를 초기화로 숨기지 않는다.
- 순번 전송은 벽시계 정확성을 보장하지 않는다. 관찰 시각은 수정하지 않으며
  서버는 기존 시간 정렬 규칙으로 타임라인을 구성한다.

세부 요구사항과 검증 시나리오는
[오프라인 활동 동기화 PRD](../PRD_MACOS_OFFLINE_ACTIVITY_SYNC.md)에 정의한다.
