# Mosemo macOS Desktop App PRD — 활동 수집 MVP

> 문서 상태: 초안 v0.1
> 기준일: 2026-09-07
> 대상 제품: Apple Silicon 기반 macOS 14 이상용 Mosemo 데스크톱 앱
> 제품 범위: 포커스 활동 관찰, 개인정보 보호, 로컬 보관과 동기화, 서버 기준 타임라인 조회

## 1. 문서 목적과 기준

오프라인 기록과 동기화의 합의된 세부 기준은
[전용 PRD](PRD_MACOS_OFFLINE_ACTIVITY_SYNC.md)와
[ADR-0003](adr/0003-persist-activity-before-sequential-upload.md)에 정리한다.
해당 범위에서 두 PRD가 충돌하면 전용 PRD를 우선한다.

이 문서는 Mosemo macOS 앱이 사용자의 실제 포커스 활동을 안전하고 신뢰성 있게 수집하고, 서버가 확정한 활동 타임라인을 사용자에게 보여 주기 위한 제품 요구사항을 정의한다.

이 PRD의 활동 수집 범위에서는 다음 기준을 적용한다.

1. 사용자에게 제공할 가치를 먼저 정의하고, 관찰·전송·표시의 책임을 구분한다.
2. 클라이언트는 관찰한 사실만 기록한다. 같은 활동인지, 새 활동인지, 이전 활동이 언제 끝났는지는 서버가 판단한다.
3. 식별 가능한 정보는 암호화된 로컬 대기열에 기록하기 전에 개인정보 정책을 적용한다.
4. 타임라인은 서버가 수락하고 투영한 결과만 표시한다.
5. 이 문서와 기존 `docs/REQUIERMENTS.md`가 활동 수집 범위에서 충돌하면, 이 문서가 채택한 최신 활동 수집 설계를 우선한다. 충돌 항목은 13절에 명시한다.

현재 저장소의 앱은 수집 가능성을 검증하는 feasibility spike다. 메모리 ring buffer와 진단 UI 등 현재 구현은 제품 요구사항의 근거로 참고할 수 있지만, 그 자체를 출시 동작으로 간주하지 않는다.

## 2. 제품 배경과 문제

사용자는 하루 동안 여러 앱과 웹페이지를 오가지만, 시간이 어디에 쓰였는지 나중에 정확히 복기하기 어렵다. 단순 앱 사용 시간은 실제 작업 대상을 설명하지 못하고, 공격적인 원문 수집은 개인정보 위험을 만든다. 네트워크 단절, 앱 재시작, 절전, 권한 변경이 발생하면 활동이 유실되거나 잘못 이어질 수도 있다.

Mosemo의 활동 수집 MVP는 다음 문제를 해결해야 한다.

- 사용자가 실제로 포커싱한 앱·창·웹 활동만 관찰한다.
- 민감한 활동은 내용이나 식별자를 남기지 않으면서도 “활동은 있었다”는 사실을 보존한다.
- 오프라인, 재시도, 응답 유실, 앱 재시작 뒤에도 관찰 순서와 중복 제거가 유지된다.
- 관찰할 수 없었던 시간과 개인정보 때문에 내용을 숨긴 시간을 서로 다르게 보여 준다.
- 클라이언트의 미전송 상태를 실제 활동으로 오인하지 않도록 서버 확정 결과만 타임라인에 표시한다.

## 3. 제품 목표

### 3.1 사용자 목표

- 별도의 수동 기록 없이 내가 포커싱했던 앱·창·웹 활동을 시간순으로 확인할 수 있다.
- 수집 중인지, 일시 정지되었는지, 동기화가 지연되는지 즉시 알 수 있다.
- 민감한 활동이 구체적인 앱·창·사이트 정보 없이 처리된다는 사실을 신뢰할 수 있다.
- 네트워크가 끊기거나 Mac을 잠갔다가 돌아와도 타임라인이 중복되거나 임의로 이어지지 않는다.

### 3.2 제품 목표

- AI 해석 이전에 신뢰할 수 있는 활동 관찰 원본과 서버 타임라인 기반을 만든다.
- 관찰 사실, 수집 공백, 개인정보 보호 상태를 명시적으로 구분한다.
- 데이터 유실과 중복을 방지하는 재시도 가능한 동기화 경로를 제공한다.
- 이후 AI 해석과 사용자 확정 의미를 원본을 변경하지 않고 추가할 수 있게 한다.

### 3.3 성공 기준

MVP는 다음 상태를 달성했을 때 성공한 것으로 본다.

- 정의된 오프라인·응답 유실·앱 재시작·잠금·절전 시나리오에서 수락 전 레코드 유실이 없다.
- 동일 요청 또는 동일 레코드의 재전송으로 타임라인 활동이 중복되지 않는다.
- 개인정보 정책에 걸린 식별 정보가 로컬 영속 대기열, 서버 전송, 로그, 진단 정보에 남지 않는다.
- 사용자가 보는 타임라인에서 정상적인 불투명 활동과 실제 수집 공백이 구별된다.
- 클라이언트 대기열의 미전송 레코드가 타임라인 활동으로 선표시되지 않는다.

타임라인 최신성, 최대 대기열 크기, 동기화 지연, CPU·메모리·배터리 목표의 수치 기준은 출시 전 확정해야 한다.

## 4. 대상 사용자와 핵심 사용 상황

### 4.1 대상 사용자

첫 번째 사용자는 Mac에서 지식 노동을 수행하며 자신의 하루 활동 흐름을 자동으로 남기고 싶은 개인 사용자다. 여러 앱과 브라우저 탭을 오가고, 네트워크가 불안정하거나 Mac을 자주 잠그는 상황에서도 기록의 연속성과 개인정보 보호를 중요하게 생각한다.

### 4.2 핵심 사용 상황

1. 사용자가 로그인하고 수집 목적과 범위를 확인한 뒤 필요한 macOS 권한을 허용한다.
2. 사용자가 활동 수집을 켜면 앱은 현재 포커스 대상을 관찰하고 상태를 메뉴 막대에 표시한다.
3. 사용자가 앱·창·탭·URL을 바꾸면 앱은 짧은 안정화 뒤 새 전체 스냅샷을 로컬 대기열에 보관한다.
4. 네트워크가 없으면 관찰은 암호화된 로컬 대기열에 남고, 연결 복구 후 순서대로 전송된다.
5. 화면 잠금·절전·권한 상실 중에는 활동을 추측하지 않고 수집 중단 상태를 기록한다.
6. 사용자가 타임라인을 열면 서버가 만든 활동 구간, 알 수 없는 활동, 수집 공백을 확인한다.

## 5. 범위

### 5.1 MVP 포함 범위

- Kakao 로그인 세션 확인과 서버 발급 기기 등록 식별자 사용
- 수집 목적·범위·개인정보 처리 방식 안내
- macOS 수집 권한 상태 확인, 요청, 복구 안내
- 활동 수집 켜기·끄기와 재시작 후 설정 복원
- 현재 포커스 앱과 포커스 창 관찰
- 지원 브라우저의 활성 탭 제목과 URL 관찰
- 개인정보 필터 적용 후 상세 또는 불투명 전체 스냅샷 생성
- 수집 중단·재개 상태 기록
- 암호화된 로컬 FIFO 대기열
- 기존 활동 단건 API를 이용한 순차 전송, 재시도, 레코드별 수락 확인
- 수집·권한·네트워크·동기화 상태 표시
- 서버가 투영한 타임라인 조회와 표시
- 민감한 원문 없이 문제를 진단할 수 있는 안전 진단 정보

### 5.2 MVP 비범위

- 이 활동 관찰 동기화 범위에서 수동 활동 작성과 집중 세션 타이머의 오프라인 동작
  (기존 `docs/REQUIERMENTS.md`의 별도 요구사항)
- AI에 의한 활동 의미, Task, Label, 집중도 또는 생산성 해석
- 사용자가 AI 제안을 수정하거나 의미를 확정하는 기능
- 복귀 지점, 보상·레벨·위젯
- 활동 병합·분할의 사용자 편집 기능
- 통계, 리포트, 인사이트
- 스크린샷, 화면 녹화, 페이지 본문, 폼 값, 클립보드 내용 수집
- 키 입력 내용, 마우스 좌표·이동 내용 수집
- 보존 기간, 개별 삭제, 내보내기 정책의 구체 값
- 서버의 물리 데이터 모델과 저장 최적화

현재 spike의 입력 발생 여부 집계와 입력 모니터링 권한은 이 PRD의 활동 수집에 필요하지 않다. 다른 제품 기능이 이를 필요로 한다면 별도 요구사항과 개인정보 검토를 거쳐야 한다.

오프라인 동기화 대상은 개인정보 필터를 거친 `activity_observation`과
`collection_state_changed` 활동 레코드다. 네트워크 단절만으로는 수집 공백을
만들지 않으며, 관찰 가능한 동안에는 두 종류의 레코드를 계속 로컬에 보관한다.
계정당 활성 기록 Device는 최대 한 대라는 제품 전제를 유지한다. 서버는 기존
Device의 로컬 대기열이 비었는지 알 수 없으므로 기존 Device의 동기화 완료를
기다리지 않고 새 Device를 사용할 수 있게 한다. 새 Device 로그인 시 기존 기록
권한을 차단하며, 기존 Device가 서버의 명시적인 기기 교체 응답을 확인하면 해당
이전 기록 권한의 미동기화 대기열을 폐기한다. 기기 전환 때만 미동기화 기록 유실을
허용하며, 새 Device에는 전환 전 유실 안내나 확인 단계를 표시하지 않는다.
오프라인인 기존 Device는 교체 사실을 확인할 때까지 로컬 수집을 계속할 수 있지만,
교체 후 기존 기록 권한으로 서버에 새 기록을 추가할 수 없어야 한다.
단일 활성 Device의 서버 강제, 기록 권한 교체와 명시적 교체 응답의 서버 계약은
이번 오프라인 동기화의 구현 범위와 분리한 별도 인증 작업이다. 위 기기 전환
정책과 FR-ONB-09는 해당 계약 제공 후 연동할 때 적용하며, 계약이 없는 현재
인증 오류를 기기 교체로 추정해 대기열을 폐기하지 않는다.
오프라인 보관 목표는 단절 시간보다 암호화 대기열의 용량 상한으로 정의한다.
상한에 도달해 더 저장할 수 없으면 조용히 오래된 레코드를 버리지 않고 수집을
중단해 알린다. 동기화나 디스크 공간 확보로 모든 용량 조건이 충분히 회복되고
사용자의 수집 설정과 필수 권한이 허용하면 자동 재개한다. 사용자가 직접 끈 수집은
자동으로 켜지 않는다. 중단과 재개를 반복하지 않도록 재개 기준에는 여유를 두며,
상한·재개 기준 수치와 경고 단계는 후속 결정이다.

이번 오프라인 동기화 구현은 온라인일 때에도 관찰을 로컬에 영속 기록한 뒤
대기열에서 전송한다. 최초 구현부터 계정별·앱 전체 용량 상한과 디스크 최소
여유 공간 기준을 적용하되, 구체적인 바이트 수는 레코드 크기 측정으로 정한다.
로컬 DB 채택 여부는 구현 선택이며, 필수 계약은 암호화된 영속 대기열과 레코드·순번·
수락 상태의 원자적인 변경이다.
활동 데이터 삭제 API와 삭제 전 기록의 재수락 방지는 삭제 기능과 함께 구현한다.
용량 부족으로 수집이 멈춘 기간을 서버 타임라인의 명시적 수집 공백으로 복구하는
기능은 후속 구현으로 남긴다. 그 전에는 앱이 수집 중단을 알리지만 타임라인에는
해당 공백이 명시되지 않을 수 있다.

## 6. 제품 원칙과 책임 경계

| 주체 | 책임 | 하지 않는 일 |
| --- | --- | --- |
| macOS 클라이언트 | 포커스 대상 관찰, 개인정보 필터, 식별자·순번 부여, 암호화 로컬 보관, 순서 전송 | 활동 동일성·경계·의미 판단 |
| 서버 수집 API | 인증, 레코드 중복·순번 충돌 확인, 필터 후 원본 보존 | 클라이언트에서 제거한 민감 정보 복원 |
| 서버 타임라인 투영 | 연속 스냅샷을 비교해 활동 구간과 공백 생성 | 관찰되지 않은 시간을 활동으로 추정 |
| macOS 화면 | 수집·동기화 상태와 서버 확정 타임라인 표시 | 미전송 대기열을 활동 타임라인으로 선표시 |

다음 개념은 반드시 분리한다.

- `상세 활동`: 표시·비교 가능한 앱·창·웹 문맥을 가진 정상 관찰
- `불투명 활동`: 관찰은 했지만 개인정보 정책에 따라 식별 정보를 저장하지 않은 정상 관찰
- `수집 공백`: 잠금·절전·권한 상실·해석 불가 등으로 실제 활동을 관찰하거나 연결할 수 없었던 구간
- `동기화 지연`: 관찰은 로컬에 안전하게 보관됐지만 아직 서버가 수락하지 않은 상태

## 7. 사용자 경험 요구사항

### 7.1 최초 실행과 온보딩

- 사용자는 Kakao로 로그인하고 현재 계정 상태를 확인할 수 있어야 한다.
- 앱은 활동 수집을 시작하기 전에 수집 대상, 수집하지 않는 정보, 불투명 활동, 서버 전송, 오프라인 보관을 설명해야 한다.
- 앱은 필요한 macOS 권한을 각각 설명하고 현재 상태와 시스템 설정으로 이동하는 방법을 제공해야 한다.
- 필수 권한이 없더라도 앱은 실행되어야 하며, 사용할 수 없는 수집 범위와 해결 방법을 보여 줘야 한다.
- 앱은 서버에서 발급받은 `deviceId`를 안전하게 저장하고 전송에 사용해야 한다.

정상 수집 경로는 로그인 → 권한 허용 → 홈 진입이며, 홈에서 수집을 시작할 때는
서버 Device 등록과 `deviceId` 저장이 이미 완료된 상태를 전제한다. 따라서 이번
오프라인 동기화 범위는 등록을 마친 Device의 연결 단절 이후부터 시작한다.

### 7.2 메뉴 막대

메뉴 막대는 항상 접근 가능한 빠른 제어면이다.

- 아이콘은 최소한 수집 중, 일시 정지, 사용자 중지, 주의 필요 상태를 구별해야 한다.
- 사용자는 메뉴에서 수집을 켜거나 끌 수 있어야 한다.
- 메뉴는 현재 권한 문제, 오프라인 여부, 미동기화 레코드 존재 여부를 원문 노출 없이 요약해야 한다.
- 용량 부족·수집 중단·복구 필요 상태는 메뉴 막대의 주의 상태와 앱 안의 지속적인 상태 표시로 알려야 한다. 첫 구현에는 별도 macOS 알림을 추가하지 않으며, 일시적인 자동 재시도에는 팝업을 띄우지 않는다.
- 사용자는 메뉴에서 메인 타임라인 창과 설정·권한 화면을 열 수 있어야 한다.
- 앱 종료는 수집 중지와 다르다는 점을 명확히 해야 하며, 재실행 시 마지막 사용자 설정에 따라 동작해야 한다.

### 7.3 메인 데스크톱 창

메인 창은 다음 영역을 제공한다.

1. 수집 상태: 현재 수집 가능 여부와 중단 이유
2. 동기화 상태: 최신 동기화 시각, 대기 중 여부, 해결이 필요한 오류
3. 타임라인: 서버가 만든 활동 구간과 공백
4. 권한 및 개인정보: 권한 상태, 수집 범위 설명, 개인정보 정책 상태

메인 창을 닫아도 사용자가 수집을 끄거나 앱을 종료하지 않는 한 메뉴 막대 앱과 수집은 계속 동작해야 한다.

### 7.4 타임라인 표시

| 서버 결과 | 사용자 표시 |
| --- | --- |
| 앱 정보가 있고 창 정보가 없거나 미수집 | 앱 활동 |
| 정상 URL만 있는 브라우저 문맥 | 웹 활동 |
| 불투명 문맥 | 알 수 없는 활동 |
| 표시 가능한 앱·웹 식별 정보가 없음 | 활동 카드를 표시하지 않음 |
| 수집 공백 | 타임라인의 공백 |

- 활동 카드는 서버가 수락하고 투영한 결과만 사용해야 한다.
- 미동기화 레코드는 타임라인에 선표시하지 않고 동기화 상태 영역에서만 알려야 한다.
- 불투명 활동과 수집 공백은 문구와 시각 표현 모두에서 구별해야 한다.
- 카드로 표시되지 않는 서버 원본이 존재할 수 있음을 타임라인이 임의의 연속 활동으로 메워서는 안 된다.
- 첫 버전은 URL 쿼리 또는 프래그먼트가 달라지면 서로 다른 활동 구간으로 표시될 수 있다.

## 8. 기능 요구사항

### FR-ONB. 계정, 동의, 권한

- **FR-ONB-01** 앱은 인증된 계정으로만 서버 수집과 타임라인 조회를 수행해야 한다.
- **FR-ONB-02** 앱은 서버 발급 `deviceId`를 사용해야 하며 임의의 로컬 기기 식별자로 대체하지 않아야 한다. 수집 가능한 홈 진입 전에 Device 등록과 `deviceId` 저장이 완료되어 있어야 한다.
- **FR-ONB-03** 앱은 최초 수집 전에 수집 범위와 개인정보 처리 방식을 안내해야 한다.
- **FR-ONB-04** 앱은 권한별 허용·거부·철회 상태를 감지하고 사용자에게 복구 방법을 제공해야 한다.
- **FR-ONB-05** 명시적 로그아웃 시 새 활동 수집과 서버 전송을 멈추고, 이전 계정의 미동기화 레코드는 해당 계정에 귀속된 암호화 대기열에 보존해야 한다. 같은 계정으로 다시 인증한 뒤에만 전송을 재개해야 한다.
- **FR-ONB-06** 일시적인 네트워크 또는 인증 확인 실패 중에는 마지막으로 확인된 계정에 새 관찰을 귀속해 로컬에 보관할 수 있어야 한다. 다른 계정으로 로그인해도 이전 계정의 레코드를 전송하거나 타임라인에 섞지 않아야 한다.
- **FR-ONB-07** 토큰 만료 시 마지막으로 확인된 계정에 로컬 수집은 계속하되 서버 전송을 멈추고 재인증을 안내해야 한다. 같은 계정으로 다시 인증한 뒤에만 해당 대기열의 전송을 재개해야 한다.
- **FR-ONB-08** 서버가 저장된 `deviceId`를 거절하면 서버 전송과 새 활동 수집을 일시 중단하고 미동기화 레코드를 보존해야 한다. 기존 레코드의 `deviceId`를 새 값으로 바꾸지 않고 복구가 필요한 상태를 알려야 한다.
- **FR-ONB-09 (별도 인증 계약 제공 후 적용)** 다른 Device 로그인 시 기존 Device의 응답이나 동기화 완료를 기다리지 않고 새 Device로 기록 권한을 전환해야 한다. 새 Device에는 전환 전 기록 유실 안내나 확인 단계를 표시하지 않는다. 기존 Device는 명시적인 기기 교체 응답을 확인하면 수집·전송을 멈추고 이전 기록 권한에 귀속된 대기열을 폐기해야 한다. 토큰 만료·일반 401·네트워크 실패·일반 Device 거절은 이 폐기 조건이 아니다. 늦게 도착한 이전 권한의 응답으로 새 인증이나 다른 계정의 대기열을 폐기하지 않아야 한다. 이 전환을 강제하는 서버 인증 계약은 이번 오프라인 동기화 구현에 포함하지 않는다.

### FR-COL. 수집 생명주기

- **FR-COL-01** 사용자는 활동 수집을 명시적으로 켜고 끌 수 있어야 한다.
- **FR-COL-02** 사용자가 선택한 수집 설정은 앱 재시작과 일반적인 OS 재부팅 뒤에도 유지되어야 한다.
- **FR-COL-03** 첫 실행부터 활동 수집을 기본으로 켜고, 사용자가 명시적으로 끈 설정은 재시작 후에도 유지해야 한다.
- **FR-COL-04** 사용자가 수집을 끄면 새 활동 관찰과 이벤트 생성을 중단해야 한다. 이미 로컬에 저장한 대기 기록의 전송은 계속할 수 있으며, 수집 중지와 동기화 중지를 동일하게 취급하지 않아야 한다.
- **FR-COL-05** 화면 잠금, 절전, 필수 권한 상실로 관찰할 수 없으면 `collection_state_changed`의 `suspended` 상태와 이유를 기록해야 한다.
- **FR-COL-06** 수집이 다시 가능해지면 `active` 상태 변경을 기록하고 새 전체 스냅샷으로 시작해야 한다.
- **FR-COL-07** 중단 전과 재개 후 활동을 하나의 연속 활동으로 클라이언트가 연결하지 않아야 한다.
- **FR-COL-08** 용량 부족으로 일시 중단한 수집은 계정별·앱 전체 대기열과 디스크 여유 공간이 모두 재개 기준을 충족하면 자동 재개해야 한다. 사용자 수집 설정이 켜져 있고 계정·Device 상태와 필수 권한이 수집을 허용할 때만 재개하며, 사용자가 직접 끈 수집은 재개하지 않아야 한다. 재개 기준에는 중단과 재개의 반복을 피할 여유를 두고, 재개 후 새 전체 스냅샷부터 기록해야 한다. 저장소 손상이나 기기 교체 등 다른 중단 사유를 용량 회복만으로 해제하지 않아야 한다.
- **FR-COL-09** 정상적인 앱 종료 요청 시 새 관찰을 멈추고 이미 대기 중이거나 진행 중인 로컬 영속 저장을 안전하게 마친 뒤 종료해야 한다. 대기열의 서버 전송 완료는 종료 조건으로 삼지 않아야 하며, 네트워크 단절이나 서버 장애 때문에 종료를 기다리게 하지 않아야 한다. 종료 시 서버 수락이 확인되지 않은 레코드는 보존하고 다음 실행에서 동일 레코드로 전송을 재개해야 한다.

### FR-OBS. 활동 관찰

- **FR-OBS-01** 클라이언트는 현재 전면 앱과 그 포커스 창만 관찰해야 한다. 백그라운드 앱이나 화면에 열린 모든 창을 열거하지 않아야 한다.
- **FR-OBS-02** 수집 시작·재개, 전면 앱 변경, 포커스 창·창 제목·활성 브라우저 탭·URL 변경 때 전체 스냅샷을 생성해야 한다.
- **FR-OBS-03** 활성 수집 중 변화가 없더라도 마지막 관찰 후 30초가 지나면 새 전체 스냅샷을 생성해야 한다.
- **FR-OBS-04** 빠른 연속 변화는 짧은 안정화 시간 뒤 마지막으로 확인된 상태 하나를 스냅샷으로 생성할 수 있다. 안정화 시간은 출시 전 측정으로 정한다.
- **FR-OBS-05** 각 스냅샷은 이전 값과의 차이가 아니라 그 시점에 알 수 있는 전체 관찰값이어야 한다.
- **FR-OBS-06** 앱 bundle ID와 표시 이름, 창, 탭 제목, URL의 수집 상태를 필드별로 독립 표현해야 한다.
- **FR-OBS-07** 앱 bundle ID가 있으면 표시 식별자로 우선 사용하고, 없으면 앱 이름을 사용할 수 있다. 둘 다 없으면 상세 활동 카드를 만들 수 없는 원본으로 처리한다.
- **FR-OBS-08** 창은 `captured`, `absent`, `unavailable`을 구별해야 한다. 빈 제목과 읽지 못한 제목도 구별해야 한다.
- **FR-OBS-09** 웹 문맥은 `not_applicable`과 `browser`를 구별하고, 브라우저일 때 탭 제목과 URL의 상태를 각각 `captured`, `absent`, `unavailable`, `redacted` 중 하나로 표현해야 한다.
- **FR-OBS-10** URL 하나만 정상적으로 관찰해도 유효한 웹 활동을 만들 수 있어야 한다.
- **FR-OBS-11** URL을 파싱할 수 없다는 이유만으로 허용된 원문 관찰을 버리거나 레코드 생성을 실패시키지 않아야 한다.
- **FR-OBS-12** 앱·창·웹 어느 정보도 얻지 못하면 상세 활동을 억지로 만들거나 값을 추측하지 않아야 한다.
- **FR-OBS-13** 클라이언트는 활동 전환 이벤트, 시작·종료 시각, 동일 활동 여부를 만들지 않아야 한다.

### FR-PRV. 개인정보 처리

- **FR-PRV-01** 개인정보 필터는 원문이 암호화 로컬 대기열, 서버 요청, 로그 또는 진단 정보에 기록되기 전에 적용되어야 한다.
- **FR-PRV-02** 개인정보 정책에 걸린 정상 활동은 `{ "kind": "opaque" }`만 저장·전송해야 한다.
- **FR-PRV-03** 불투명 활동에는 앱·창·도메인·URL·해시·규칙 이름 등 대상을 식별할 수 있는 정보를 포함하지 않아야 한다.
- **FR-PRV-04** `data:`와 `javascript:` URL은 값을 버리고 `redacted`와 `embedded_content_scheme` 이유를 기록해야 한다.
- **FR-PRV-05** 허용 길이를 넘는 URL은 일부를 잘라 보관하지 않고 `redacted`와 `length_exceeded` 이유를 기록해야 한다.
- **FR-PRV-06** 보관 가능한 URL은 브라우저가 관찰한 문자열을 그대로 유지해야 한다. 클라이언트가 query 또는 fragment를 제거하거나 서버가 정규화할 것을 전제로 바꾸지 않아야 한다.
- **FR-PRV-07** 창·탭 제목이 길이 제한을 넘으면 허용된 앞부분, `truncated: true`, 원래 바이트 길이를 기록해야 한다.
- **FR-PRV-08** 화면 이미지·화면 녹화·키 입력 내용·마우스 좌표·폼 값·페이지 본문을 수집하지 않아야 한다.

### FR-QUE. 로컬 대기열과 식별자

- **FR-QUE-01** 개인정보 필터링, `event_id`와 `sequence` 부여, 암호화된 로컬 대기열 기록은 하나의 원자적 처리여야 한다.
- **FR-QUE-02** 순번만 소비하고 레코드를 잃거나, 레코드를 저장하고 순번 상태를 잃는 중간 상태를 만들지 않아야 한다.
- **FR-QUE-03** 일반적인 앱 재시작, OS 재부팅, 네트워크 실패 뒤에도 미수락 레코드와 같은 Device의 다음 순번을 복구해야 한다.
- **FR-QUE-04** 대기열 또는 순번 상태를 복구할 수 없으면 임의로 순번을 재사용하거나 누락된 레코드를 만들어 내지 않아야 한다. 수집과 전송을 멈추고 복구가 필요한 상태를 알려야 한다.
- **FR-QUE-05** 계정과 Device가 다른 대기열의 레코드 또는 순번 상태를 서로 합치지 않아야 한다.
- **FR-QUE-06** 로컬 대기열은 저장 시 암호화되어야 하고 키는 macOS 보안 저장소에서 관리해야 한다.
- **FR-QUE-07** 관찰 사실은 개인정보 필터 적용과 로컬 영속 기록이 완료된 뒤에만 기록된 것으로 취급해야 한다. 저장 공간 부족 등으로 기록할 수 없으면 수집 중단과 사용자 주의 필요 상태를 알리고, 관찰을 조용히 버리거나 기록된 것으로 표시하지 않아야 한다.
- **FR-QUE-08** 서버가 해당 레코드의 수락 또는 동일 레코드 재전송 성공을 확인하기 전에는 로컬 대기열에서 제거하지 않아야 한다. 응답 유실은 수락 실패로 단정하지 않고 같은 레코드를 재전송해야 한다. 명시적인 기기 교체로 인한 이전 기록 권한의 대기열 폐기는 FR-ONB-09의 예외를 따른다.
- **FR-QUE-09** 네트워크 연결 여부와 무관하게 모든 활동 레코드를 로컬에 영속 기록한 뒤, 전송기는 대기열에 저장된 레코드만 서버에 보내야 한다.
- **FR-QUE-10** 최초 구현부터 계정별·앱 전체 대기열 상한과 디스크 최소 여유 공간을 확인해야 한다. 어느 한도에 도달해도 미수락 레코드를 자동 삭제하지 않아야 한다.
- **FR-QUE-11** 용량 부족에 따른 수집 중단만으로 기존 대기열의 전송을 중단하지 않아야 한다. 전송·저장이 가능한 상태에서는 수락된 레코드를 제거해 공간을 확보하고, 동기화 또는 디스크 공간 회복 뒤 FR-COL-08의 자동 재개 조건을 다시 확인해야 한다.
- **FR-QUE-12** 앱 업데이트로 로컬 저장 형식이 바뀌어도 기존 미동기화 레코드와 같은 Device의 다음 순번을 보존해야 한다. 이전 형식을 읽거나 원래 전송 내용을 유지하며 변환하되 `eventId`·`sequence`·`observedAt`과 개인정보 필터 후 본문을 변경하지 않아야 한다. 읽기·변환·복구가 실패하면 기존 대기열과 순번 상태를 초기화하지 않고 수집·전송을 멈춘 뒤 복구 필요 상태를 표시해야 한다. 변환 중 앱이 종료되어도 기존 기록을 잃지 않아야 한다.

### FR-SYN. 단건 순차 전송과 복구

- **FR-SYN-01** 앱 프로세스 안의 동기화 작업이 영속 대기열에서 같은 Device의 가장 오래된 미수락 레코드를 읽어 기존 `POST /api/v1/activities`로 보내야 한다. 별도 OS 프로세스는 두지 않는다.
- **FR-SYN-02** 같은 Device에서는 한 번에 한 레코드만 전송하고, 해당 레코드의 수락을 확인하기 전에는 다음 레코드를 보내지 않아야 한다.
- **FR-SYN-03** 요청 전후에 `eventId`, `sequence`, `observedAt`, 개인정보 필터 후 본문을 바꾸지 않아야 한다. 네트워크 오류나 응답 유실 뒤에는 저장된 동일 레코드를 다시 보내야 한다.
- **FR-SYN-04** `201 accepted` 응답의 `eventId`가 전송한 레코드와 일치할 때만 해당 레코드를 수락된 것으로 처리하고 대기열에서 제거해야 한다. 동일한 재전송의 최초 수락 결과도 같은 방식으로 처리한다.
- **FR-SYN-05** 네트워크 오류와 재시도 가능한 서버 오류에는 사용자 조작 없이 자동 재시도해야 한다. 응답의 `Retry-After`를 존중하고 지수 backoff와 jitter를 적용해야 한다. 네트워크 연결 표시만으로 수락을 간주하지 않아야 한다.
- **FR-SYN-06** 인증·Device 오류 또는 `eventId`·순번·본문 충돌은 성공으로 취급하거나 레코드를 건너뛰지 않아야 한다. 대기열을 보존하고 자동 재시도 가능 여부와 사용자 조치 필요 여부를 구분해야 한다. 명시적인 기기 교체 응답만 FR-ONB-09에 따라 이전 기록 권한의 대기열을 폐기하며, 이를 서버 수락 성공으로 표시하지 않는다.
- **FR-SYN-07** 보낼 레코드가 없으면 빈 주기 요청을 만들지 않아야 한다. 30초 관찰 스냅샷 자체는 정상 레코드이므로 대기열에 들어간 뒤 전송 대상이 된다.
- **FR-SYN-08** 앱 실행 중 네트워크와 인증이 전송 가능한 상태로 회복되면 동기화 작업을 재개해야 한다. 앱이 종료된 동안의 대기 기록은 보존하고 다음 실행·재인증 후 재개하며, 메인 창을 닫아도 메뉴 막대 앱이 실행 중이면 전송을 계속할 수 있어야 한다.
- **FR-SYN-09** 이번 구현은 배치 API나 서버의 연속 순번 ACK를 요구하지 않는다. FR-ONB-09의 기기 교체 폐기 예외를 제외하고, 로컬 대기열의 순차 전송과 서버의 레코드별 멱등 수락으로 모든 저장 레코드가 수락되면 최종 타임라인이 해당 원본에 수렴해야 한다.
- **FR-SYN-10** 맨 앞 레코드의 `eventId`·순번·본문 충돌 또는 검증 오류로 전송이 막히면 후속 전송을 멈추고 실패 레코드와 뒤의 대기 기록을 보존해야 한다. 사용자 수집 설정과 계정·Device·권한·저장소 상태가 수집을 허용하면 새 관찰은 용량 한도까지 계속 로컬에 보관해야 한다. 동기화에 조치가 필요함을 표시하고 실패 레코드를 자동 삭제하거나 건너뛰지 않아야 한다. 용량 한도에 도달하면 FR-COL-08·FR-QUE-10의 수집 중단·재개 정책을 따른다.
- **FR-SYN-11** 첫 구현에서는 수동 동기화 재시도 버튼을 제공하지 않는다. 토큰 만료 시 전송은 재인증을 기다렸다가 자동 재개한다. 충돌·검증 오류는 같은 요청을 반복해도 해소되지 않을 수 있으므로 자동 반복 전송을 멈추고 오류 상태와 기록을 보존한다. 이러한 오류의 원인을 고치거나 저장소를 복구하는 절차는 후속 설계 대상으로 두며, 재시도로 해결된다고 가정하지 않는다.
- **FR-SYN-12** 사용자가 수집을 끄더라도 앱이 실행 중이고 인증·Device·네트워크·저장소 상태가 전송을 허용하면 이미 저장된 대기 기록의 동기화를 계속해야 한다. 네트워크가 회복되면 수집 설정을 다시 켜지 않고도 기존 대기 기록의 자동 전송을 재개해야 한다. 명시적 로그아웃은 FR-ONB-05에 따라 수집과 전송을 모두 멈추고 기록을 보존한다.

### FR-DEL. 활동 데이터 삭제와 미동기화 기록

이 절의 결과 보장은 향후 활동 데이터 삭제 기능과 함께 구현한다.

- **FR-DEL-01** 활동 데이터 삭제가 완료된 뒤에는 삭제 이전에 관찰됐지만 아직 전송되지 않은 레코드가 늦게 도착해도 활동 타임라인에 다시 나타나지 않아야 한다.
- **FR-DEL-02** 삭제 사실을 확인한 클라이언트는 해당하는 미동기화 레코드를 폐기해야 한다. 삭제 시 오프라인이었던 다른 설치가 옛 레코드를 보내더라도 서버는 재수락하지 않아야 한다.
- **FR-DEL-03** 삭제와 업로드가 겹쳐도 삭제 완료 이후에는 삭제 이전 관찰이 남거나 다시 생성되지 않아야 한다. 이를 보장하는 식별·경합 처리 계약은 후속 설계에서 정한다.

### FR-TIM. 시간 정보

- **FR-TIM-01** 각 레코드는 UTC `observed_at`, 당시 `timezone_id`, `utc_offset_minutes`를 포함해야 한다.
- **FR-TIM-02** 로컬에 저장한 `observed_at`은 네트워크 복구나 재전송 시각으로 바꾸지 않아야 한다.
- **FR-TIM-03** 앱이 오프라인 수집 중 큰 벽시계 변경을 감지하면 영향을 받은 기간의 시간 순서 정확성을 보장할 수 없다고 사용자에게 알려야 한다. 저장된 `observed_at`을 추정값으로 교정하지 않아야 한다.

현재 단건 API에는 `clock_epoch_id`와 `monotonic_ns`가 없다. Device 순번만으로는
벽시계 변경 전후의 정확한 관찰 시각을 복원할 수 없다. 첫 구현은 감지 가능한 큰
변경을 로컬에서 알리되, 재부팅 중 발생한 변경처럼 감지하지 못할 수 있는 경우와
서버 타임라인에 불확실성을 표시하는 계약은 후속 설계 대상으로 둔다.

### FR-UI. 상태와 타임라인

- **FR-UI-01** 사용자는 수집, 권한, 네트워크, 동기화의 현재 상태를 원문 노출 없이 확인할 수 있어야 한다.
- **FR-UI-02** 동기화 오류는 사용자 조치가 필요한 오류와 자동 재시도 중인 상태를 구별해야 한다.
- **FR-UI-03** 타임라인은 서버가 투영한 관찰 활동 구간과 수집 공백만 표시해야 한다.
- **FR-UI-04** 연속 불투명 활동은 하나의 알 수 없는 활동 구간으로 표시될 수 있어야 한다.
- **FR-UI-05** 불투명 활동을 상세 활동과 병합하거나 앱 전환으로 표현하지 않아야 한다.
- **FR-UI-06** 서버가 화면 표시 불가로 판정한 원본은 카드로 표시하지 않되, 앞뒤 활동을 연결하는 근거로 사용하지 않아야 한다.
- **FR-UI-07** 오프라인 대기열 개별 레코드의 제목·URL·앱 정보를 미리 보여 주지 않아야 한다.
- **FR-UI-08** 미동기화 레코드의 건수와 동기화 상태를 원문 노출 없이 보여 주고, 서버가 수락하기 전에는 해당 레코드를 활동 타임라인에 표시하지 않아야 한다.
- **FR-UI-09** 첫 구현에서는 동기화 재시도 버튼 없이 일시적 오류의 자동 복구 상태, 재인증 필요 상태, 충돌·검증 오류에 따른 전송 중단 상태를 구별해 표시해야 한다. 전송이 멈춘 상태를 정상 동기화 중으로 표시하지 않아야 한다.
- **FR-UI-10** 첫 구현의 용량 부족·수집 중단·복구 필요 알림은 메뉴 막대의 주의 상태와 앱 안의 지속적인 상태 표시로 제공해야 한다. 수집 또는 전송 중단 사유와 대기 기록이 보존되어 있는지 여부를 원문 노출 없이 알려야 한다. 별도 macOS 알림은 후속 필요에 따라 검토하며, 일시적인 자동 재시도에는 팝업을 띄우지 않아야 한다.

## 9. 데이터와 서버 계약 요약

이번 구현은 기존 `POST /api/v1/activities`의 단건 계약을 사용한다. 각 레코드는
온라인 여부와 무관하게 먼저 로컬 대기열에 저장되며, 앱 안의 동기화 작업이
같은 Device의 레코드를 한 건씩 순서대로 전송한다. 서버는 같은 `eventId`와 같은
내용의 재전송에 최초 수락 결과를 반환하지만, 연속 순번 ACK는 제공하지 않는다.

### 9.1 식별자 책임

| 필드 | 범위 | 변경 시점 | 용도 |
| --- | --- | --- | --- |
| 로컬 계정 식별자 | 클라이언트 대기열 | 인증된 계정이 바뀔 때 | 다른 계정의 레코드와 전송 상태 분리 |
| `deviceId` | 서버 등록 앱 설치 | 서버의 Device 등록이 바뀔 때 | 계정에 귀속된 관찰 주체 확인 |
| `eventId` | 활동 레코드 | 로컬 영속 기록 시 | 단건 재시도와 서버 중복 제거 |
| `sequence` | 같은 Device의 레코드 | 새 레코드마다 증가 | 로컬 FIFO 순서와 서버의 중복 순번 충돌 확인 |

`eventId`와 `sequence`는 같은 레코드의 재시도 내내 유지한다. 서버는 순번의
유일성은 확인하지만 연속성이나 계정 타임라인의 순서를 `sequence`로 판정하지
않는다. 타임라인은 관찰 시각을 기준으로 정렬한다.

### 9.2 클라이언트가 보내는 레코드

단건 요청은 다음 두 형식 중 하나다.

- `activity_observation`: 상세 또는 불투명 전체 스냅샷
- `collection_state_changed`: `active` 또는 `suspended`와 수집 가능성에 관한 이유

공통 필드는 `deviceId`, `eventId`, `sequence`, `observedAt`, `timezoneId`,
`utcOffsetMinutes`다. `clock_epoch_id`와 `monotonic_ns`는 현재 공개 요청에 없다.

### 9.3 ACK 최소 요구

서버는 최초 저장과 동일한 재전송 모두 `201`로 `eventId`, `status: accepted`,
최초 `receivedAt`을 반환한다. 클라이언트는 응답의 `eventId`와 상태가 현재
레코드에 맞을 때에만 해당 레코드를 대기열에서 제거한다. 응답 유실 시에는
수락 여부를 추측하지 않고 동일한 레코드를 다시 보낸다.

### 9.4 필요한 서버 의존 기능

- 인증된 Device 등록과 `deviceId` 발급·계정 소유권 검증
- `eventId` 기준 동일 본문 재전송 수락과 다른 본문 충돌 감지
- 같은 Device의 `sequence` 충돌 감지와 늦거나 역순으로 도착한 레코드 수락
- 필터 후 원본 보존과 타임라인 투영의 원자적 처리
- 서버 확정 활동 구간·공백 조회 API
- 클라이언트가 재시도·중단을 구별할 수 있는 안정적인 오류 코드와 `Retry-After`

현재 서버 OpenAPI를 요청·응답·오류 계약으로 삼는다. macOS 앱은 오류 문자열을
파싱해 복구를 결정하지 않아야 한다. 배치·스트림 계약은 적체 동기화 성능이
단건 경로로 부족하다고 확인될 때 별도로 설계한다.

## 10. 비기능 요구사항

### NFR-PRV. 개인정보와 보안

- 전송은 TLS를 사용해야 한다.
- 배포 빌드의 인증 토큰과 로컬 암호화 키는 Keychain 등 macOS 보안 저장소에 보관해야 한다. 개발 빌드는 배포 전환을 전제로 앱 전용 SQLite를 임시 사용할 수 있다.
- 로그, crash report, metric, 안전 진단에는 제목, URL, 사용자·기기 식별자, 인증 정보, 요청·응답 본문을 넣지 않아야 한다.
- 개인정보 필터는 네트워크 연결 여부와 무관하게 같은 입력에 같은 정책을 적용해야 한다.
- 불투명 활동은 식별 가능한 내부 구분자나 안정적인 해시를 가져서는 안 된다.

### NFR-REL. 신뢰성과 정합성

- 전달 보장은 at-least-once 전송과 서버 멱등 처리의 조합으로 제공해야 한다.
- 앱 강제 종료 시에도 원자적으로 커밋된 대기열 레코드와 다음 순번을 복구해야 한다.
- ACK 처리는 멱등해야 하며 이미 제거한 레코드에 같은 ACK가 다시 와도 순서 상태가 손상되지 않아야 한다.
- 대기열 손상과 키 접근 실패를 조용히 초기화하지 않고 사용자 조치가 필요한 상태로 표시해야 한다.

### NFR-EFF. 성능과 자원 사용

- 백그라운드 수집은 사용자의 전면 앱 입력과 화면 전환을 방해하지 않아야 한다.
- 브라우저 관찰 주기, 안정화 시간, 단건 전송 속도와 재시도 간격은 실제 CPU·메모리·에너지·누락률 측정으로 정해야 한다.
- 대기열 적체가 커져도 메인 UI를 한 번에 전부 읽어 정지시키지 않아야 한다.
- 서버 타임라인 조회는 페이지 또는 기간 단위로 제한할 수 있어야 한다.

### NFR-ACC. 접근성과 상태 전달

- 수집과 동기화 상태를 색상만으로 구별하지 않아야 한다.
- VoiceOver가 메뉴 막대 상태, 권한 문제, 동기화 오류, 활동과 공백을 읽을 수 있어야 한다.
- 사용자가 행동해야 하는 오류에는 문제의 영향과 다음 조치를 함께 제공해야 한다.

### NFR-OBS. 안전한 관측 가능성

- 운영 지표는 수집 상태 변경 수, 대기열 레코드 수·최고 수위, 재시도 횟수, ACK 지연, 무결성 오류 코드를 확인할 수 있어야 한다.
- 운영 지표만으로 앱·창·사이트·사용자 활동 내용을 복원할 수 없어야 한다.
- 자동화 테스트, 수동 런타임 검증, 장시간 측정 결과를 구분해 기록해야 한다.

| AC-25 | 용량 부족이나 복구 필요로 수집·전송이 중단되거나 일시적 오류를 자동 재시도함 | 중단·복구 필요 상태는 메뉴 막대와 앱 안에서 지속적으로 확인할 수 있고, 중단 사유와 대기 기록 보존 여부를 원문 없이 알 수 있다. 첫 구현에는 별도 macOS 알림이 없으며 일시적 자동 재시도는 팝업을 띄우지 않는다. |

## 12. 출시 검증 게이트

- 단건 수락 응답 확인 후 삭제와 응답 유실·중복 수락 응답 처리 테스트
- `eventId`·순번·본문 충돌 또는 검증 오류 시 실패 레코드와 후속 대기열 보존·후속 전송 중단·용량 한도까지 새 관찰 보관·조치 필요 상태 유지 테스트
- 일시적 오류의 자동 재시도·재인증 후 자동 재개와 충돌·검증 오류에 대한 자동 반복 전송 중단 테스트
- 앱 재시작 뒤 Device별 미수락 레코드·다음 순번 복구 테스트
- 앱 업데이트 후 이전 형식의 대기 레코드·다음 순번 보존, 변환 중 강제 종료, 읽기·변환 실패 시 원본 보존·수집 및 전송 중단 테스트
- 사용자 수집 중지 후 기존 대기열 전송 지속·연결 회복 시 자동 전송 재개·수집 설정 유지와 로그아웃 시 전송 중단 테스트
- 정상 앱 종료 시 대기 중·진행 중 로컬 저장 완료, 서버 응답이 없는 경우에도 종료, 다음 실행에서 미수락 레코드 복구와 동일 요청 재전송 테스트
- 수집·전송 중단 사유와 대기 기록 보존 여부의 지속적인 상태 표시, 일시적 자동 재시도 시 팝업 미표시 검증
- 용량 부족 시 수집만 중단하고 전송 가능한 대기열은 계속 처리하는 테스트, 공간 회복 후 자동 재개와 사용자 중지·권한 상실·다른 중단 사유 유지 테스트, 중단·재개 기준 주변에서 반복 전환을 막는 테스트
- 기기 교체 시 B의 즉시 사용·이전 권한의 업로드 거절, 명시적인 교체 응답으로 해당 이전 대기열만 폐기하는 경계 테스트는 별도 인증 계약 제공·연동 작업에서 검증하며 이번 오프라인 동기화의 출시 게이트에는 포함하지 않음
- 관찰 시각 불변성·timezone 변경·감지 가능한 큰 벽시계 변경 시 사용자 알림 테스트; 재부팅 중 변경의 탐지 범위는 후속 설계 뒤 검증
- 서버 OpenAPI와 Swift DTO·오류 처리 계약 테스트
- 로그·진단·crash metadata의 금지 필드 정적 검사

### 실제 macOS 런타임 검증

- 최초 권한 허용, 거부, 실행 중 철회, 다시 허용
- 앱·창·지원 브라우저 탭·URL 변화 관찰
- 잠금, 절전, 사용자 수집 중지와 재개
- 오프라인 적체와 연결 복구
- 업로드 응답 유실과 재전송
- 앱 강제 종료와 재실행
- 장시간 실행 중 CPU·메모리·에너지·대기열 증가
- VoiceOver와 시스템 화면 배율에서 상태·타임라인 확인

자동화, 수동 런타임, 장시간 측정 중 실제로 수행하지 않은 검증은 통과로 표시하지 않는다.

## 13. 기존 문서·spike와의 충돌 정리

| 기존 문서 또는 현재 spike의 관점 | 이 PRD에서 채택한 관점 |
| --- | --- |
| 클라이언트가 활동 시작·종료와 전환 이벤트를 생성 | 클라이언트는 순서 있는 전체 관찰 스냅샷만 생성하고 서버가 구간과 경계를 판단 |
| URL에서 query allow-list를 적용하고 fragment를 제거 | 허용 가능한 URL은 관찰 원문 전체를 보존하고, 저장 불가 URL은 일부 수정하지 않고 전체 redacted 처리 |
| 보호 활동에 앱 유형 또는 앱 이름을 유지 | 불투명 활동에는 어떤 식별자, 해시, 규칙 이름도 유지하지 않음 |
| 로컬 spool 활동을 Event Log에 즉시 표시 | 미전송 레코드는 동기화 상태로만 표시하고 활동 타임라인은 서버 투영 결과만 표시 |
| 현재 spike는 사용자가 추적을 시작해야 수집 | 앱 실행 시 추적을 기본으로 시작하고 사용자가 끄면 중단 |

이 표는 기존 문서 전체를 폐기하지 않는다. 활동 수집 MVP와 직접 충돌하는 항목만 후속 문서 정리 대상임을 나타낸다.

## 14. 확정 전 남은 제품 결정

다음 항목은 구현 전에 하나씩 확정해야 한다.

1. **브라우저 지원 범위**: 기존 요구사항의 Chrome 우선 출시를 유지할지, 현재 spike의 Firefox 관찰을 MVP에 포함할지
2. **필드 제한**: 창·탭 제목의 최대 바이트 수, URL 최대 바이트 수
3. **관찰 안정화**: 빠른 변화에 적용할 debounce 시간과 브라우저별 관찰 주기
4. **단건 적체 처리 성능**: 전송 속도 제한, 재시도 backoff와 jitter, 허용할 적체 해소 시간. 배치 API는 단건 경로의 부족이 측정될 때 검토한다.
5. **로컬 용량 정책의 남은 결정**: 계정별·앱 전체 최대 바이트 수, 디스크 여유 공간의 수치 기준, 경고 단계, 중단과 재개 사이에 둘 여유의 정량 기준. 용량 회복 후 자동 재개와 사용자 중지 유지 조건은 FR-COL-08·FR-QUE-11로 확정했다. 상한과 여유 공간 검사는 최초 구현에 포함하고 수치는 레코드 크기 측정으로 정한다.
6. **개인정보 정책 관리**: 기본 불투명 규칙, 사용자가 규칙을 보고 바꿀 수 있는지, 정책 변경의 적용 시점
7. **인증·삭제 경계의 남은 결정**: 토큰 만료 뒤 재인증 UX, 거절된 Device의 안전한 복구 절차, 활동 데이터 삭제 시 오래된 레코드를 식별·거절하는 계약과 경합 처리, 계정 삭제 시 로컬 대기열 처리. Device 전환 방침은 FR-ONB-09로 확정했다. Device와 기록 권한을 연결할 서버 세션 계약, 일반 401·만료와 구분할 교체 응답 및 이전 권한의 식별은 별도 인증 작업이며 이번 오프라인 동기화 구현 범위에 포함하지 않는다. 해당 계약 제공 전에는 기기 교체를 추정한 대기열 폐기를 구현하지 않는다. 일반 로그아웃·계정 전환·토큰 만료·Device 거절은 FR-ONB-05~08을 따른다. FR-DEL은 삭제 기능 구현과 함께 적용한다.
8. **무결성 오류 복구**: `eventId`·Device 순번 충돌·검증 오류의 원인 수정과 대기열·순번 상태 손상 시 복구 가능한 범위, 로컬 저장 형식의 버전 관리와 구체적인 변환 절차. 앱 업데이트 시 보존과 실패 시 중단 정책은 FR-QUE-12로 확정했다. 첫 구현의 자동 재시도·중단 정책과 수동 재시도 버튼 생략은 FR-SYN-05·FR-SYN-10~11로 확정했다. 영구 오류를 반복 요청으로 해결하거나 대기열을 자동 초기화하지 않는다.
9. **타임라인 조회 UX**: 기본 기간, 페이지 방식, 새 서버 투영 결과의 갱신 방식, 빈 구간 표현
10. **정량 품질 기준**: 감지 지연, 타임라인 최신성, 동기화 지연, 장시간 CPU·메모리·에너지 목표
11. **클라이언트 계약 검증**: 현재 서버 OpenAPI의 활동 단건 생성·타임라인·Device 등록, 오류 코드와 충돌 응답을 생성 클라이언트에 반영
12. **오프라인 시각**: 큰 벽시계 변경을 판정할 정량 기준, 재부팅 중 변경의 탐지 가능 범위, 경고의 유지 기간·표시 위치 및 서버 타임라인에 불확실성을 표현할지 여부. 저장된 `observedAt`은 변경하지 않는다.

위 결정은 이 문서의 확정된 책임 경계와 개인정보 원칙을 바꾸지 않는 범위에서 구체화한다. 원본·AI 제안·사용자 확정 의미의 분리나 불투명 활동과 수집 공백의 구분을 바꾸려면 별도 제품·도메인 결정을 기록해야 한다.
