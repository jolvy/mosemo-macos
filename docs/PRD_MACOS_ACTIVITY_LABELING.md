# Mosemo macOS 앱 PRD — 활동 라벨 검토와 집계

> 문서 상태: 초안
> 기준일: 2026-09-20
> 범위: 서버의 관찰 활동 구간에 대한 라벨 제안 검토, 사용자 확정, 라벨 타임라인과 대시보드 표시

## 1. 목적과 기준

사용자는 관찰된 앱·창·웹 문맥이 자신에게 어떤 활동이었는지 확인하고, AI의 라벨
제안을 나중에 모아 고친 뒤 확정할 수 있어야 한다. macOS 앱은 서버가 제공한
관찰 사실과 라벨 상태를 보여 주고 사용자 선택을 전달한다. 앱에서 활동 의미를
독자적으로 추정하거나 관찰 활동 구간을 새로 만들지 않는다.

이 문서는 [활동 수집 MVP PRD](PRD_MACOS_ACTIVITY_COLLECTION.md) 이후의 라벨
기능을 다룬다. 수집 MVP에서 AI 라벨링을 제외한 결정은 유지한다. 라벨과 활동
흐름에 관한 이전 [요구사항](REQUIERMENTS.md)과 충돌하면 이 문서 및
[서버 라벨링 스펙](https://github.com/jolvy/mosemo/issues/25)의 현재 결정을
우선한다. 서버의 공개 OpenAPI가 클라이언트 계약의 기준이며, 라벨 API가 공개되기
전에는 이 문서의 화면과 동작을 구현 완료로 취급하지 않는다.

## 2. 앱의 책임

- 인증된 계정의 라벨 목록, 라벨 타임라인, 검토 대기 항목, 라벨별 활동 시간을
  서버에서 조회한다. 다른 계정의 임시 선택을 보여 주거나 재사용하지 않는다.
- AI가 제안한 라벨과 사용자가 확정한 라벨을 명확히 구분해 표시한다. 제안이
  없거나 근거가 부족한 항목은 미분류 또는 검토 대기로 보여 준다.
- 사용자가 제안을 그대로 승인하거나 활성 라벨 또는 미분류로 바꾼 뒤 명시적으로
  확정할 수 있게 한다. 화면에서 선택을 바꾼 것만으로 확정·집계하지 않는다.
- 시간상 이어지고 라벨 및 확정 상태가 같은 관찰 활동 구간만 타임라인의 한 행으로
  묶는다. 행에 여러 구간이 포함되면 확정 동작이 그 구간 모두에 적용됨을 알 수
  있게 한다. 떨어진 같은 라벨은 별도 행으로 남긴다.
- 서로 다른 여러 검토 항목에 각자의 선택을 지정하고 한 번에 확정할 수 있게
  한다. 활동이 쌓이는 동안 매 구간의 승인을 요구하지 않는다.
- 이미 확정한 라벨을 나중에 정정할 수 있게 하고, 서버가 반영한 최신 확정값과
  집계를 다시 조회해 보여 준다. 새 확정 이력으로 기존 미확정 제안을 화면에서
  몰래 교체하지 않는다. 확정·정정 이력은 서버가 같은 사용자의 다음 제안에 바로
  참고하며, 앱은 이를 위한 별도 개인화 승인 단계를 요구하지 않는다.
- 사용자 정의 라벨의 생성, 이름 변경, 보관을 제공한다. 이름을 바꾸면 과거
  활동의 표시 이름도 새 이름으로 보인다. 보관 라벨은 과거 확정 기록에 남지만
  새 활동의 선택 목록에서는 빠진다.
- 서버가 제공한 오늘의 확정 라벨별 총 시간을 대시보드에 보여 준다. 검토 대기,
  확정된 미분류, 불투명 활동 시간은 각각 별도 값으로 표시한다. 미확정 제안을
  라벨별 잠정합계에 넣지 않는다.

## 3. 라벨 타임라인

1. 활동 카드는 서버가 확정한 관찰 구간과 라벨 상태를 바탕으로 그린다. 로컬에서
   아직 전송하지 않은 활동은 확정된 관찰이나 라벨 활동으로 선표시하지 않는다.
2. 관찰 활동 구간 하나에는 대표 라벨이 최대 하나다. 앱·창이 바뀌어도 활동의
   의미가 같으면 같은 라벨을 표시할 수 있다. 하나의 긴 관찰 구간을 앱 화면에서
   시간별로 분할해 서로 다른 라벨을 붙이지 않는다.
3. 같은 라벨이라도 중간에 다른 라벨, 다른 확정 상태, 불투명 활동, 수집 공백,
   관찰되지 않은 시간이 있으면 새 행으로 표시한다. 시작과 끝이 같은 0초 관찰
   구간도 시간순 기록에서 누락하지 않는다.
4. 불투명 활동은 개인정보 보호로 식별 정보가 없는 정상 활동으로 따로 표시한다.
   라벨 선택과 확정 동작을 제공하지 않는다. 수집 공백은 관찰하지 못한 시간으로
   표시하고 활동으로 간주하지 않는다.
5. 아직 열린 관찰 활동 구간에는 라벨 제안이나 확정 동작을 요구하지 않는다.
   서버가 구간의 종료를 확인한 뒤 검토 대상이 된다.

예를 들어 타임라인에는 `10:00–10:05 coding`, `10:10–10:15 shopping`,
`10:20–10:25 coding`을 별도 행으로 보여 준다. 대시보드에는 사용자가 모두
확정한 경우에만 `coding 10분`, `shopping 5분`을 보여 준다.

## 4. 검토와 오류 처리

1. 검토 화면은 AI 제안, 사용자의 현재 선택, 확정 상태를 구분한다. 사용자가
   선택을 바꾼 뒤 취소하거나 화면을 벗어나도 서버 확정값과 집계는 바뀌지 않는다.
2. 한 행을 승인하면 그 행에 들어 있는 모든 관찰 활동 구간이 확정된다. 여러
   행을 제출할 때는 각 행의 선택을 함께 보낸다. 서버가 요청 성공을 확인한 뒤에만
   확정으로 표시한다.
3. 네트워크 오류나 인증 실패가 나면 성공으로 표시하지 않는다. 사용자의 미제출
   선택을 검토 화면에 남기고 재시도 또는 재로그인 후 새로고침할 수 있게 한다.
   오래된 검토 화면의 선택이 최신 확정값과 충돌하면 현재 서버 상태를 보여 주고
   다시 선택하게 한다.
4. 보관된 라벨을 가리키는 옛 제안은 기록상 보여 주되, 확정 전에 활성 라벨이나
   미분류를 다시 선택하게 한다. 서버에서 새 제안으로 재분석했다면 기존 제안이
   바뀐 사실을 사용자에게 표시한다.
5. 관찰 구간은 늦게 도착한 원본 때문에 재구성될 수 있다. 앱은 관찰 타임라인의
   `segmentId`를 영구 라벨 식별자로 보관하지 않는다. 서버가 영향 받은 항목을
   다시 검토 대상으로 돌리면 이를 현재 상태로 표시한다.

## 5. 라벨별 활동 시간

- 기본 화면은 계정 시간대의 오늘을 보여 준다. 날짜를 가로지르는 구간은 서버가
  해당 날짜에 속하는 시간만 합산한 결과를 사용한다. 앱은 화면 행의 시작·종료
  시각을 더해 공식 합계를 다시 계산하지 않는다.
- 라벨별 합계는 사용자가 확정한 관찰 활동 구간만 포함한다. 확정 전 제안,
  열린 관찰 활동 구간, 수집 공백은 어떤 라벨의 시간에도 더하지 않는다.
- 확정된 미분류는 `미분류 〇분`, 아직 검토하지 않은 시간은 `검토 대기 〇분`,
  불투명 활동은 `불투명 활동 〇분`으로 구분한다. 0초 관찰 구간은 타임라인에서
  보존하지만 시간 합계에는 0초만 기여한다.
- 라벨 정정이나 이름 변경 뒤에는 서버의 최신 합계와 표시 이름을 반영한다.

## 6. 검증 기준

- 고정된 서버 응답으로 제안·편집 중 선택·확정 라벨을 서로 구분해 표시하는지
  확인한다. 한 행 확정, 여러 행의 서로 다른 선택 일괄 확정, 미분류 확정,
  확정 후 정정을 확인한다.
- 연속된 같은 라벨·같은 상태만 묶고, 다른 라벨·상태·불투명 활동·수집 공백·
  미관찰 시간이 사이에 있으면 분리하는지 확인한다. 0초 구간을 잃지 않는지
  확인한다.
- 미확정 라벨 제안이 대시보드 라벨별 합계에 나타나지 않고, 검토 대기·확정된
  미분류·불투명 활동 시간이 구분되는지 확인한다.
- 제출 실패와 최신 상태 충돌에서 확정 성공을 잘못 표시하지 않는지 확인한다.
  서버 OpenAPI가 제공되면 생성 클라이언트와 앱의 요청·응답 계약을 검증한다.

기본 라벨의 정확한 이름과 개수는 아직 정해지지 않았다. 위 `coding`과
`shopping`은 타임라인 동작을 설명하는 예시이며 기본 라벨 목록이 아니다.

## 7. 범위 밖

- 타이머 기반 집중 세션과 집중 판단.
- `활동 흐름` 생성, 컨텍스트 스위칭 분석, 관찰 활동 구간 내부의 수동 시간 분할.
- 불투명 활동 라벨링, 미확정 제안의 라벨별 잠정합계, 승인 없는 자동 확정.
- macOS 앱 내부의 개인화 모델 학습이나 사용자별 자동 적용 규칙 승인 화면.
