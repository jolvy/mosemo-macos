# Mosemo macOS 오프라인 활동 기록과 동기화 PRD

> 기준일: 2026-09-29
> 상태: 합의된 요구사항. Testing Decisions의 주 검증 경계는 사용자 확인 대기.
> 대상: 등록된 Device에서 수집하는 활동 관찰과 수집 상태 변경

## Problem Statement

사용자는 네트워크가 잠시 끊기거나 서버 응답을 받지 못하더라도 이미 기록한 활동을 잃지 않고, 연결이 회복되면 별도 조작 없이 서버 타임라인에서 확인하고 싶다. 앱 재시작과 업데이트도 대기 기록을 지워서는 안 된다. 서버에 기록되었지만 응답이 유실된 경우를 실패로 단정하면 재전송으로 중복을 만들 수 있다.

미동기화 활동 레코드는 서버 수락을 아직 확인하지 못한 원본 사실이다. 서버에는 이미 반영되었을 수도 있으며, 관찰 타임라인 항목이나 수집 공백과 같지 않다. 오프라인 보관은 단절 시간 대신 저장 용량으로 제한한다.

## Solution

온라인과 오프라인 모두 개인정보 필터를 적용한 활동 레코드를 암호화된 영속 대기열에 먼저 기록한다. 앱 내부 전송기가 같은 Device의 레코드를 순번대로 하나씩 기존 활동 등록 API로 보내고, 일치하는 수락 응답을 확인한 레코드만 제거한다. 일시적 장애는 자동 재시도하고, 사용자 조치가 필요한 오류는 기록을 보존한 상태로 알린다.

저장 한도에 도달하면 새 수집을 멈추고 기존 기록의 전송은 가능한 동안 계속한다. 충분한 공간이 회복되고 사용자의 수집 설정과 계정·Device·권한 조건이 허용하면 자동 재개한다. 서버가 수락한 원본이 모두 반영되면 최종 관찰 타임라인이 해당 원본에 수렴하는 것을 목표로 한다.

## User Stories

1. As an 활동 기록 사용자, I want 네트워크가 끊겨도 활동을 로컬에 보관하고 싶다, so that 연결 회복 후 기록을 확인할 수 있다.
2. As an 활동 기록 사용자, I want 온라인에서도 전송 전에 기록을 보존하고 싶다, so that 요청 도중 장애에도 활동을 잃지 않는다.
3. As an 개인정보를 보호하려는 사용자, I want 개인정보 필터가 저장 전에 적용되기를 원한다, so that 허용하지 않은 정보가 대기열에 남지 않는다.
4. As an 개인정보를 보호하려는 사용자, I want 대기 기록이 암호화되기를 원한다, so that 로컬 저장 내용을 보호할 수 있다.
5. As an 활동 기록 사용자, I want 저장된 레코드가 순번대로 전송되기를 원한다, so that 후속 요청이 앞선 기록을 건너뛰지 않는다.
6. As an 활동 기록 사용자, I want 응답 유실 시 같은 기록이 재전송되기를 원한다, so that 유실 없이 중복 수락을 방지한다.
7. As an 활동 기록 사용자, I want 서버 수락 확인 전 기록이 유지되기를 원한다, so that 연결 표시만으로 기록이 삭제되지 않는다.
8. As an 활동 기록 사용자, I want 네트워크와 일시적 서버 오류가 자동 복구되기를 원한다, so that 매번 재시도 버튼을 누르지 않는다.
9. As an 활동 기록 사용자, I want 앱 재시작과 OS 재부팅 후 대기열이 복구되기를 원한다, so that 기록과 다음 순번이 유지된다.
10. As an 활동 기록 사용자, I want 앱 업데이트와 저장 형식 변환 중에도 기록이 유지되기를 원한다, so that 업데이트가 활동 유실을 만들지 않는다.
11. As an 활동 기록 사용자, I want 저장 한도에 도달하면 수집 중단을 알림받기를 원한다, so that 기록하지 못한 활동을 기록된 것으로 오해하지 않는다.
12. As an 활동 기록 사용자, I want 용량 부족에도 기존 기록이 삭제되지 않기를 원한다, so that 저장했던 활동을 나중에 동기화할 수 있다.
13. As an 활동 기록 사용자, I want 수집이 용량 때문에 멈춰도 기존 기록이 전송되기를 원한다, so that 대기열 공간을 확보할 수 있다.
14. As an 활동 기록 사용자, I want 공간 회복 후 조건이 맞으면 자동 수집 재개를 원한다, so that 수집 설정을 다시 바꿀 필요가 없다.
15. As an 수집을 직접 중지한 사용자, I want 공간 회복이 내 중지 설정을 바꾸지 않기를 원한다, so that 수집 의사가 존중된다.
16. As an 활동 기록 사용자, I want 수집을 꺼도 기존 기록은 동기화되기를 원한다, so that 이전 활동의 전송을 마칠 수 있다.
17. As an 로그아웃하는 사용자, I want 수집과 전송은 멈추고 기록은 유지되기를 원한다, so that 같은 계정과 Device로 재인증 후 이어갈 수 있다.
18. As an 토큰이 만료된 사용자, I want 기존 계정으로 로컬 기록을 계속하고 재인증 후 전송하기를 원한다, so that 인증 대기가 기록 유실로 이어지지 않는다.
19. As an 여러 계정을 사용하는 사용자, I want 계정과 Device의 대기열이 분리되기를 원한다, so that 다른 계정으로 이전 활동이 전송되지 않는다.
20. As an 활동 기록 사용자, I want 충돌이나 검증 오류가 있는 기록과 후속 기록이 유지되기를 원한다, so that 오류를 숨기기 위해 기록이 누락되지 않는다.
21. As an 활동 기록 사용자, I want 전송 충돌 중에도 가능한 범위에서 새 활동을 저장하기를 원한다, so that 전송 장애가 곧바로 수집 장애가 되지 않는다.
22. As an 활동 기록 사용자, I want 저장소 손상이나 복호화 실패를 명확히 알기를 원한다, so that 초기화로 기록을 잃지 않고 복구 필요 상태를 인지한다.
23. As an 활동 기록 사용자, I want 창을 닫아도 실행 중인 메뉴 막대 앱이 동기화하기를 원한다, so that 창을 계속 열어 둘 필요가 없다.
24. As an 앱을 종료하는 사용자, I want 로컬 저장은 안전하게 마치고 서버 응답은 기다리지 않기를 원한다, so that 종료가 장시간 동기화에 묶이지 않는다.
25. As an 활동 기록 사용자, I want 대기 건수와 동기화 상태를 원문 없이 확인하기를 원한다, so that 개인정보 노출 없이 지연을 이해한다.
26. As an 활동 기록 사용자, I want 서버 수락 전 기록이 타임라인에 표시되지 않기를 원한다, so that 로컬 상태와 서버 결과를 혼동하지 않는다.
27. As an 활동 기록 사용자, I want 재전송 시 관찰 시각이 유지되기를 원한다, so that 복구 시각이 실제 활동 시각을 덮어쓰지 않는다.
28. As an 활동 기록 사용자, I want 감지 가능한 큰 시계 변경의 한계를 알기를 원한다, so that 시간 순서가 정확하다고 오해하지 않는다.
29. As an 활동 기록 사용자, I want 중단 사유와 기록 보존 여부를 지속적으로 확인하기를 원한다, so that 필요한 조치를 판단할 수 있다.

## Implementation Decisions

### 전제와 책임

- 로그인 → 권한 허용 → 홈 흐름에서 서버 Device 등록과 `deviceId` 영속 보관이 완료되어 있다고 가정한다. Device는 계정에 귀속된 앱 설치이며 물리 장비 식별자가 아니다.
- 대상은 `activity_observation`과 `collection_state_changed`다. 개인정보 필터, 영속 대기열, 동기화 조정기, 인증 조정기, 수집 생명주기, 상태 표시 모듈이 협력한다. 관찰 타임라인 투영은 서버 책임으로 유지한다.
- 단일 활성 기록 Device는 제품 전제다. 서버의 동시 로그인 차단·기록 권한 교체 강제는 별도 인증 작업이며 이번 구현과 출시 검증의 선행 조건으로 추가하지 않는다.

### 저장과 전송

- 모든 레코드는 개인정보 필터를 거쳐 영속 저장한 뒤에만 전송한다. `eventId`, Device별 `sequence`, 필터 후 본문 저장과 다음 순번 갱신은 원자적이다. 필터 이전 정보는 영속 기록하지 않는다.
- 대기열과 순번 상태는 계정·Device별로 분리한다. 일반 재시작·ACK·로그아웃으로 순번을 재사용하거나 초기화하지 않는다. 저장 완료 전 관찰은 기록된 것으로 표시하지 않는다.
- 대기열은 저장 시 암호화하고 키는 macOS 보안 저장소에서 관리한다. 저장 기술 선택은 이 요구사항의 본질이 아니다. 기존 작업의 SQLite·암호화 대기열은 재사용 후보이며 완료 증거가 아니다.
- 별도 OS 프로세스 없이 앱 내부 비동기 작업이 Device별 최저 순번의 대기 레코드를 기존 `POST /api/v1/activities`로 전송한다. 한 Device의 요청은 한 번에 하나이며 수락 확인 후 다음 레코드를 보낸다. 빈 대기열에 빈 주기 요청을 보내지 않는다.
- 재시도는 저장된 `eventId`·`sequence`·`observedAt`·필터 후 본문을 그대로 사용한다. `201` 응답의 일치하는 `eventId`와 `status: accepted`를 확인해야 제거한다. 동일 레코드 재전송은 최초 수락 결과와 `receivedAt`을 반환하는 기존 멱등 계약을 사용한다. 응답 유실과 ACK 제거 중 종료도 같은 레코드 재전송으로 복구한다.
- 순번은 전송 순서를 보장한다. 서버 시간 정렬은 `observedAt`, `receivedAt`, `eventId`의 기존 규칙을 따른다. 순번 전송이 잘못된 벽시계를 교정한다고 보장하지 않는다.

### 용량과 오류 정책

| 조건 | 새 수집 | 기존 전송 | 대기 기록 |
| --- | --- | --- | --- |
| 네트워크·재시도 가능한 서버 오류 | 저장 가능한 동안 계속 | 지수 backoff·jitter로 자동 재시도, Retry-After 준수 | 보존 |
| 토큰 만료·일시적 인증 확인 실패 | 마지막 확인 계정으로 가능한 동안 계속 | 유효 인증 회복까지 대기 | 보존 |
| 명시적 로그아웃 | 중단 | 중단 | 같은 계정·Device 재인증을 위해 보존 |
| 일반 Device 거절 | 중단 | 중단 | 보존, 다른 Device로 재귀속 금지 |
| 선두 레코드 충돌·검증 오류 | 허용되는 동안 용량 한도까지 계속 | 선두와 후속 전송 중단, 같은 오류의 자동 반복 금지 | 선두와 후속 모두 보존 |
| 용량 한도·디스크 여유 공간 부족 | 중단 | 가능한 동안 계속 | 자동 삭제 금지 |
| 대기열·순번 손상, 복호화·변환 실패 | 중단 | 중단 | 초기화·삭제 없이 보존 |

- 최초 구현부터 계정별 상한, 앱 전체 상한, 디스크 최소 여유 공간을 모두 검사한다. 단절 기간이나 TTL에 따른 자동 폐기는 하지 않는다.
- 동기화·공간 확보 후 모든 용량 조건이 충분히 회복되면 재개를 평가한다. 사용자 수집 설정, 계정·Device, 필수 권한과 다른 중단 사유가 모두 허용해야 한다. 중단 기준과 재개 기준에 여유를 두어 반복 전환을 방지한다. 재개 후 새 전체 스냅샷을 기록하며 놓친 관찰을 만들어 내지 않는다.
- 수동 동기화 재시도 버튼은 제공하지 않는다. 같은 계정·Device의 재인증 후 자동 전송을 재개한다. 영구 오류의 원인 수정과 복구 도구는 후속 설계 대상이며 삭제·건너뛰기·식별자 변경으로 해결하지 않는다.

### 생명주기·시간·표시

- 수집 설정을 꺼도 기존 대기열은 전송 가능 조건에서 계속 처리한다. 로그아웃은 두 작업을 모두 중단한다. 이전 인증의 늦은 응답이 새 인증이나 다른 계정의 기록을 변경하지 않도록 한다.
- 정상 종료는 새 수집을 멈추고 대기 중이거나 진행 중인 로컬 저장을 안전하게 마친다. 서버 응답이나 대기열 소진은 기다리지 않는다. 비정상 종료에서 이미 영속 저장된 기록은 보존하지만 아직 저장되지 않은 관찰까지 보장하지는 않는다.
- 메인 창 닫기는 앱 종료와 다르다. 메뉴 막대 앱이 실행 중이면 전송을 계속하고, 완전히 종료되면 다음 실행에서 복구한다.
- 저장 형식 변경 시 기존 기록과 다음 순번을 보존하는 이전 형식 읽기 또는 안전한 변환을 제공한다. 변환 중 종료에도 기존 데이터를 잃지 않는다. 전송 내용을 변경하거나 실패 시 새 저장소로 초기화하지 않는다.
- UTC 관찰 시각과 당시 시간대·UTC offset을 보존한다. 감지 가능한 큰 벽시계 변경은 시간 정확성 한계를 알리되 저장 시각을 추정 교정하지 않는다.
- UI는 대기 건수, 자동 복구 중·재인증 필요·조치 필요 상태와 중단 사유·보존 여부를 표시한다. 대기열 레코드의 제목·URL·앱 정보를 미리 표시하지 않으며 서버 타임라인에 선표시하지 않는다. 로그와 진단에 제목·URL·계정 식별자·토큰·본문을 노출하지 않는다.
- 주의가 필요한 상태는 메뉴 막대와 앱 안에서 지속 표시한다. 첫 구현은 별도 macOS 알림을 추가하지 않고 일시적 재시도 팝업도 띄우지 않는다.

## Testing Decisions

주 검증 경계 제안은 기존 OfflineActivityCoordinator의 공개 동작이다. 실제 임시 암호화 대기열과 제어 가능한 전송기를 연결해 입력 관찰·인증·수집 설정·저장 조건·전송 결과에 따른 보존 내용, 요청 순서, 건수와 사용자 상태를 검증한다. 이 경계의 채택은 사용자 확인 대기다.

기존 OfflineActivityCoordinatorTests의 단건 순서·ACK·응답 유실·충돌·로그아웃·계정 격리를 선례로 삼고, EncryptedActivityQueueTests의 재개방·용량 실패·암호화와 MosemoAPITests의 전송 계약 검증을 필요한 범위에서 보완한다. SQL 테이블 구조, 내부 플래그, 비공개 함수 호출 횟수를 요구사항의 증거로 삼지 않는다.

1. 온라인·오프라인 관찰이 저장 완료 전 전송되지 않으며 재개방 뒤 동일 내용과 다음 순번이 복구된다.
2. 선두 ACK 전 후속 요청이 없고, 응답 유실·수락 후 로컬 제거 전 종료에도 같은 레코드를 재전송한다. 불일치 ACK는 제거 근거가 아니다.
3. 일시적 오류의 자동 재시도, Retry-After 준수, 같은 계정·Device 재인증 후 재개를 검증한다.
4. 로그아웃·다른 계정·일반 Device 거절에서 보존·전송 중단·분리가 유지되고 늦은 응답이 새 상태에 영향을 주지 않는다.
5. 충돌·검증 오류는 선두와 후속 전송을 막고 모두 보존하지만 가능한 동안 새 관찰을 저장한다.
6. 계정별·전체 상한과 디스크 여유 부족 각각에서 보존·수집 중단·기존 전송을 검증한다. 공간 회복 시 자동 재개, 사용자 중지·권한 상실·다른 중단 사유 유지, 기준 근처 반복 전환 방지를 검증한다.
7. 정상 종료에서 로컬 저장 완료와 서버 응답 비대기를 검증하고, 다음 실행의 복구를 확인한다.
8. 이전 저장 형식 fixture와 변환 중 종료·실패에서 내용과 순번 보존을 확인한다. 손상·키 접근·복호화 실패는 삭제나 초기화 없이 복구 필요 상태로 이어져야 한다.
9. 필터 이전 민감 정보가 저장·전송·로그·진단에 없고, 대기열 원문과 미수락 활동이 UI에 노출되지 않는지 확인한다.
10. 관찰 시각·시간대 불변성과 감지 가능한 시계 변경 경고를 검증한다. 수락된 원본의 서버 타임라인 수렴은 기존 등록·조회 계약에 대한 통합 시나리오로 확인한다.

API 응답 해석은 기존 client의 HTTP 테스트로 보완한다. 실제 macOS의 창 닫기·종료·권한·보안 저장소 접근과 상태 표시는 runtime 검증으로 확인한다. 필요한 경우 서버 등록·조회 통합 검증은 실제 PostgreSQL과 인증된 HTTP 경계를 사용한다. 새로운 서버 API나 내부 SQL 순서 검증은 요구하지 않는다.

## Out of Scope

- 배치 API, 연속 순번 ACK, 별도 daemon과 앱 종료 중 전송.
- 서버 단일 활성 Device 강제, 토큰 차단·기록 권한 교체, 명시적 교체 응답과 이전 권한 대기열 폐기 구현. 이 인증 작업은 현재 기능의 구현·출시 필수 조건에 포함하지 않는다.
- 용량 부족으로 중단된 기간을 서버의 명시적 `capture_gap`으로 복구하는 기능.
- 수동 재시도 버튼, 영구 오류 복구 UI·도구, 별도 macOS 알림.
- 시계 교정, 재부팅 중 시계 변경의 완전한 탐지, clock epoch·monotonic API 확장과 서버 타임라인의 불확실성 표시.
- 활동 데이터 삭제 후 과거 대기열 재생 방지, 계정 삭제 정책, 미등록 Device의 최초 오프라인 온보딩.
- 포커스 타이머·수동 활동 편집, 브라우저 수집 범위와 개인정보 규칙 전체의 재설계.

## Further Notes

- 계정별·전체 바이트 상한, 디스크 여유 기준, 경고·재개 여유 수치는 실제 레코드 크기를 측정해 출시 전에 정한다. 재시도·처리량 수치와 큰 시계 변경의 기준·경고 유지 조건도 세부 설계에서 정한다. 보존·중단·자동 재개 원칙은 확정되어 있다.
- 별도 인증 정책에서는 B를 즉시 사용하게 하기 위해 기기 전환에 한해 A의 미동기화 기록 유실을 허용하고 B에게 사전 안내하지 않는다. 서버의 명시적 교체 계약이 제공되기 전에는 일반 401을 이 예외로 해석하지 않는다. 서버 ADR-0006이 이 정책을 소유한다.
- 현재 로컬 작업에는 대기열과 조정기의 미커밋 구현이 있다. 이 문서는 해당 작업의 완성이나 테스트 통과를 선언하지 않는다. 후속 구현은 기존 변경을 보존하며 합의된 요구사항과의 차이를 확인한다.
- 이 문서는 활동 수집 전체 PRD를 보완한다. 오프라인 동기화 범위의 세부 기준은 이 문서를 우선하고, 설계 선택의 이유는 클라이언트 ADR-0003에 기록한다.
